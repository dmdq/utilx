文本 Diff 的动态规划：编辑距离、最长公共子序列，与三方合并的冲突判定

技术笔记
2026-11-24有条工具团队

为什么逐行对齐是错的#

最朴素的文本对比是「第 i 行对第 i 行」——两个版本一行行比下去，不同就标红。它的问题在没有对齐概念：原文开头插入一行，之后所有行都错位一格，diff 报告整篇皆红，真正的改动淹没在噪声里。合格的 diff 必须先回答「哪些行是同一行」——即寻找两个序列的最长公共子序列（LCS），公共骨架对齐之后，骨架之外的就是增删。

编辑距离：一张 (m+1)×(n+1) 的表#

字符级 diff 的地基是编辑距离的动态规划。定义 dp[i][j] = 把 str1 前 i 个字符变成 str2 前 j 个字符的最少操作数，边界是 dp[i][0]=i、dp[0][j]=j（删光或插满），转移看末字符：

str1[i-1] === str2[j-1] : dp[i][j] = dp[i-1][j-1]        // 白送，对角走
否则                     : dp[i][j] = min(dp[i-1][j], dp[i][j-1]) + 1

注意这个实现里 min 只取了「删一个」和「插一个」，没有「替换」——它是只允许插入删除的编辑距离，数学上正比于 LCS：dp[m][n] = m + n − 2·LCS(m,n)。后果是「替换一个字符」的代价是 2（删旧 + 插新），经典 Levenshtein（带替换操作、代价 1）是另一张表。对高亮显示来说这个差别无伤大雅：反正替换最终渲染成一段红一段绿。

回溯从 (0,0) 走到 (m,n)：当前字符相等输出「不变」并对角走，否则比较左边与上边谁的值小——走删（str1 多了）或走插（str2 多了）。DP 表填完是 O(m×n) 的时间与空间，几千字的文本完全无压力；真要对比两个大文件，才需要 Myers 这类 O(N+D) 的算法（D 是差异数，git 的选择，差异小时飞快）。

行级 LCS：把字符换成「行」#

文档对比的粒度应该是行。把每行当作一个原子符号（先规范化——去行尾空白、可选忽略大小写），套同一个 LCS DP：

dp[i][j] = a[i]===b[j] ? dp[i+1][j+1]+1 : max(dp[i+1][j], dp[i][j+1])

实现里 DP 表是反向填的（从右下角往左上），好处是回溯可以贪心：从 (0,0) 出发，行相等输出 same 并双双前进；否则看 dp[i+1][j] >= dp[i][j+1]——下方的值更大就先输出 del（删旧行），否则输出 add（增新行）。一趟走完，增删改序列就是 diff 报告。行级对比的另一个工程红利：换行符差异、尾随空格这些噪声可以在规范化时吸收，避免「整行标红只因为句尾多了个空格」。

三方合并：冲突不是「都改了」，是「改到了同一处」#

两方 diff 之上还有一层常见需求：基准版 base 分出两个修改版 A、B，想知道合并会不会打架。判定逻辑跑两次 diff：base→A 与 base→B，各自得到操作序列后按行号区间求交——

  • 只有 A 改了某区间：合并采纳 A 的改动；
  • 只有 B 改了：采纳 B；
  • A、B 都改了同一区间且改得不一样：真冲突，标记出来人工裁决；
  • 都没改或改得相同：原样保留。

冲突的判定单位是「base 的行区间」而非「内容」——A 改了第 3 行、B 改了第 4 行是两个不相交区间，各自安全合并；A、B 都重写了第 3 行才是冲突。git merge 的冲突块 <<<<<<< / ======= / >>>>>>> 就是这个逻辑的输出格式，rebase 逐个提交重放时同一套判定跑 N 遍。三方对比工具的另一个用法是「两份 AI 产出对比」——看看两个模型各改了基准文本的哪些位置，改动是否重叠。

从工具到工程#

Diff 是那种「看着简单、边界极多」的问题：粒度（行/词/字符）、规范化（空白/大小写）、对齐稳定性（启发式挪动匹配块让 diff 更可读）……工具页面把这些做减法收成「粘贴两段文本、选个粒度、看高亮」。上手：🔧 文本对比 （行/词/字符三粒度，可选忽略空白与大小写）与 🔧 文本三方对比 （base/A/B 三栏，冲突行高亮提示）；文本工程同族的还有 🔧 行操作（排序去重提取） 与 🔧 Markdown 编辑器 ，收在写作者工具箱。文本的另一类疑难杂症——编码乱掉的逆向修复——见乱码修复那篇。

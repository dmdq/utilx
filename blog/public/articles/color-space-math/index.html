颜色空间数学：HEX 之外的三个坐标系，HSL 与 HSV 为什么是两个东西

技术笔记
2026-11-24有条工具团队

同一个颜色，三套坐标#

RGB 是机器的坐标系：三通道各 0–255，笛卡尔式直白，显示器物理上就这么发光。但人调色时想的不是「红 255 绿 87 蓝 51」，而是「橙红、饱和一点、亮一点」——色相（H）、饱和度（S）、明度（L/V）的圆柱坐标系才是直觉的语言。于是前端日常充满转换：设计稿给 HEX，CSS 变量用 HSL，Figma/PS 取色器是 HSV（工程师软件常叫 HSB）。三者转换是纯函数，几十行代码——但每一步都值得问一句「为什么是这个公式」。

HEX 的解析先热个身：#FF5733 是六个十六进制字符按 RRGGBB 切三段 parseInt；三位缩写 #F53 按「每字符自乘复制」展开成 #FF5533——split('').map((c,i) => i===0 ? c : c+c) 这个展开顺序要在拼回字符串时保持位置，是三位色解析最常见的下标错乱现场。

色相：最大通道决定你站在哪个扇区#

HSL 与 HSV 共享同一条色相（H）计算。色相的几何本质：把 RGB 立方体沿 (0,0,0)–(255,255,255) 对角线压扁，投影是六边形，红黄绿青蓝紫六段各占 60°。计算时先找最大通道——它决定你在哪个 120° 大扇区：

  • max = R：色相落在红区，h = ((G−B)/chroma + (G<B ? 6 : 0)) / 6——(G−B)/chroma 给出扇区内偏移，G<B 时差为负要 +6 绕回（这就是代码里那个神秘 +6 的来历）；
  • max = G：h = ((B−R)/chroma + 2) / 6（+2 平移到绿扇区）；
  • max = B：h = ((R−G)/chroma + 4) / 6（蓝扇区）。

除以 6 归一化到 0–1，展示时乘 360 变角度。灰色（三通道相等）没有色相，h = 0 是约定不是计算。

饱和度的分母之谜：为什么亮度过半要换公式#

HSL 的饱和度是公式里最有戏剧性的一段：

L = (max + min) / 2
S = L > 0.5 ? chroma / (2 − max − min) : chroma / (max + min)

其中 chroma = max − min。分母为什么按 L 过半切换？把两个分支通分看：max+min = 2L，2−max−min = 2(1−L)——统一形式其实是 S = chroma / (2·min(L, 1−L))，即色度除以「当前亮度下还能容纳的最大色度」。L 靠近 0（全黑）或 1（全白）时这个容量趋近 0，一点点 chroma 就是高饱和——符合直觉：暗红也是「饱和的红」。这是 HSL 对「饱和」的感知化定义，直除 max+min 在亮端会算出错误的低饱和。

HSV 的饱和度则完全不同：S = chroma / max，V = max——它把「白点」定义为 V=1，饱和度衡量的是「离白有多远」，黑色直接 V=0 不参与。两个 S 不是同一个量：hsl(50%,100%,50%) 与 hsv(50%,100%,100%) 数值上都是「满饱和半亮度/满值」，显示的颜色却分别是中黄与亮黄。

HSL 与 HSV：中点与最大值的分野#

两个空间最大的分歧在第三根轴：HSL 的 L = (max+min)/2 是中点，HSV 的 V = max 就是最大通道。后果在调色操作上非常直观——

  • 「加白」：HSL 里 L→1、S 保持，路径是竖直向上；HSV 里 V 保持 1、S 下降，路径是水平向轴心。加白让 HSV 饱和度掉、加黑让 HSL 饱和度不掉——两套滑块的行为差异全源于此；
  • 纯色（如纯红 RGB(255,0,0)）在 HSV 里是 (0°,100%,100%)——顶点就是纯色；在 HSL 里是 (0°,100%,50%)——纯色在半程。设计师说「HSV 更像颜料直觉（V=1 才有最鲜的颜色）」、程序员发现「HSL 的 L 梯度更像感知亮度」，两边都没错，它们优化的目标不同。

顺带泼一盆冷水：HSL/HSV 都不是感知均匀的——S=100% 的黄色看起来比 S=100% 的蓝色亮得多，因为人眼对绿黄频段敏感。要做无障碍配色（对比度、色盲安全），得到 CIELAB 这类感知均匀空间里算，WCAG 的对比度公式用的也是 RGB 加权的相对亮度，不是 HSL 的 L。调色板生成器「同 H 不同相位」生成的色板看起来总是黄亮蓝暗，根子在这里。

## 60 个字符的自包含宇宙

数据库里存密码的那行字符串，`$2b$10$N9qo8uLOickgx2ZMRZoMye...` 一共 60 个字符，四个 `$` 切出三段信息：**版本号 2b、成本因子 10、盐 22 字符 + 哈希 31 字符**。最有设计感的地方是它自包含——验证时不需要额外的盐字段，成本参数也不用另存一张配置表，一切都在这 60 个字符里。`compareSync(密码, 哈希)` 的第一步就是把串拆开，取出盐和成本，用同样的参数重算一遍再比对：**验证不是解密，是复现**。

里面那 53 个字符（22+31）不是标准 base64。bcrypt 用自己的字母表：`./` 开头，接大写 A-Z、小写 a-z、数字 0-9——顺序和标准 base64 完全不同，且不带 `=` 填充。22 字符装的是 **16 字节（128 位）盐**，31 字符装 23 字节哈希输出（184 位）。所以同一个密码每次哈希结果都不一样——盐是随机的，彩虹表（预算好的「密码→哈希」大字典）对它彻底失效：攻击者必须为每个盐单独算一张表，等于彩虹表退化成暴力破解。

## 成本因子：让攻击者也按指数付钱

bcrypt 的内核是 **EksBlowfish**（Expensive Key Schedule）。标准 Blowfish 的密钥编排本身就不便宜——521 轮迭代填充 P 数组和 S 盒；bcrypt 把这个过程再重复 2^cost 次，密码和盐交替参与。cost=10 就是 1024 轮密钥编排，每轮又内含 521 次填充——最终把 24 字节的魔法串 `OrpheanBeholderScryDoubt` 用算好的密钥 ECB 模式加密 64 次，取前 23 字节作哈希输出。

这个设计的精妙在于**成本可调且指数计价**：cost 每加 1，时间翻倍。本站工具里实测，浏览器里纯 JS 实现 cost=4 只要几毫秒，cost=12 要十几秒——差 256 倍，正是 2^8。摩尔定律让 CPU 每年快一点，防御方只要在登录系统里把 cost 加 1，攻击者的字典成本立刻翻倍。选型经验：让单次哈希落在**100–250ms**（服务器登录可接受的上限），今天的桌面 CPU 大约是 cost 10–12。

## 为什么 GPU 破解它不划算

MD5/SHA 这类通用哈希是纯 ALU 流水线运算，GPU 上万核心并行、ASIC 直接电路化，攻防比价一边倒。bcrypt 不一样：Blowfish 密钥编排的每一步都在查 **4KB 的 S 盒**，而且下一次查哪一格取决于上一次的结果——数据依赖的串行链条让 GPU 的 SIMD 并行施展不开，S 盒又超出了单核能吃满的高速缓存甜区。历史上 GPU 版 bcrypt 实现相对 CPU 的加速比只有个位数倍数，对比 SHA-1 的成百上千倍，等于**把攻击者的硬件优势没收了**。

代价也是真的：bcrypt 故意慢，**只能用于密码这种低频场景**（注册、登录），给文件算校验和用它就是自虐。顺带一提族谱：PBKDF2 用 HMAC 迭代次数扛（OWASP 现行建议 SHA-256 版 60 万次），实现最广但 GPU 加速有效；bcrypt 用 S 盒串行扛；scrypt 和 Argon2 再进一步用**内存硬**（大量内存写入让 GPU/ASIC 的内存带宽成为瓶颈）——Argon2id 是如今密码学竞赛选出的新标准。迁移不必急：bcrypt 至今仍是「可继续用」的选项，新系统再直接上 Argon2id。

## $2a、$2b、$2y：三个版本号是一部补丁史

- **$2a**：1999 年 OpenBSD 的原始版本，也是流传最广的版本号；
- **$2x / $2y**：当年 crypt_blowfish（PHP 生态主力实现）发现对高位字节密码存在符号扩展 bug，`$2x` 标记「按有 bug 的旧算法算」、`$2y` 标记「修正版」；
- **$2b**：2014 年又爆出 cost 高位回绕 bug，OpenBSD 顺势发行 $2b 作为「按正确方式实现」的声明。

对使用者的影响只有一条：**验证器要三个版本都认**（站内工具解析盐与成本的正则就是 `/\$2[aby]\$(\d+)\$/`），生成新哈希统一写 $2b。三个版本对 ASCII 密码的输出其实一致，混用历史数据不会炸。

## 72 字节截断：最著名的暗坑

Blowfish 的 P 数组扩展只消化密码的**前 72 字节**，bcrypt 全盘继承。这意味着 `密码A` 和 `密码A + 后面随便 100 个字符` 哈希出来一模一样——用户以为加长更安全，实际在 72 字节后按了没反应的键盘。更老版本的实现还有 NUL 截断问题（密码里出现 `\0` 字节直接截断）。工程上的稳妥做法：密码预哈希一次再喂 bcrypt（常见 `base64(HMAC-SHA256(key, password))`），既绕开长度限制又躲开 NUL。做密码校验工具时这条边界必须在文档里写明——「不一致」的测试用例里就该有一组 72 字节截断对。

## 盐、比较与配套工具

验证环节还有两个纪律：**比较必须恒定时间**（逐字节短路比较的耗时差异会泄露前缀匹配长度，成熟的 bcrypt 库内部已处理，手写比对循环时别忘了）；**换盐即换哈希**——同一密码、同一盐、同一 cost 结果可复现（这是「验证=复现」成立的前提），盐一换结果全变。这也是为什么工具页上「哈希比较」两串不同不能断言密码不同：可能只是盐不同。想自己拆解这 60 个字符，可以用 {{< tool id="bcrypt-generator" >}}BCrypt哈希生成器{{< /tool >}}（自定义成本因子生成、内置 cost 4–12 基准测试，能直观看到指数涨价）和 {{< tool id="bcrypt-verify" >}}Bcrypt验证{{< /tool >}}（粘贴哈希验证密码，三版本通吃）；生成侧还有同源的 {{< tool id="bcrypt-generate" >}}Bcrypt加密{{< /tool >}}。想对比「快哈希为什么不能存密码」，{{< tool id="sha-generator" >}}SHA系列哈希{{< /tool >}}和 {{< tool id="argon2-hash" >}}Argon2哈希{{< /tool >}}可以并排跑；配一个 {{< tool id="password-generator" >}}随机密码生成器{{< /tool >}} 就是完整的密码卫生套件，收在[隐私保护工具包](/collections/privacy-shield/)专题里。

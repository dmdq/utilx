## 一个看似能用的错误方案

「每 600 毫秒响一次」最直觉的实现是 `setInterval(play, 600)`——播出来确实像节拍器，但练琴的人半分钟后就开始皱眉：忽快忽慢。根源在于 JS 定时器的两个承诺缺一：浏览器只保证回调**不早于**指定时刻触发，不保证准时；主线程稍微一忙（GC、重排、别的脚本），回调就延后十几甚至上百毫秒。更糟的是误差会累积：每一拍的迟到都成为下一拍的基准，几分钟内漂移到人耳可闻。

为什么节拍器对精度的要求格外苛刻？人耳对节奏错位的敏感度在 10ms 量级，两位乐手合奏时几毫秒的抖动就能感知「抢拍」「拖拍」。浏览器的 UI 时钟天生达不到这个精度，必须换一座钟。

## 两座时钟：轮询泵与音频硬件钟

Chris Wilson 在《A Tale of Two Clocks》里给出的方案如今是 WebAudio 精确定时的标准姿势，全站 {{< tool id="online-metronome" >}}在线节拍器{{< /tool >}}采用的正是这套口径：

```text
setInterval(scheduler, 25)          // 轮询泵：只管「看看有没有该排的拍」
scheduler():
  while (nextNoteTime < audioCtx.currentTime + 0.120) {   // 120ms 前瞻窗
    osc.start(nextNoteTime)         // 拍点预排进音频硬件时钟
    nextNoteTime += 60 / bpm        // 按拍长逐拍推进
  }
```

关键在于 `osc.start(when)` 的语义：`when` 是 **AudioContext 时间轴**上的时刻，由音频硬件的采样时钟驱动——48kHz 采样率下精度是 1/48000 秒级。声音一旦排进队列，何时发声与 JS 主线程再无关系：页面再卡、GC 再重，拍点纹丝不动。

两座时钟各司其职：`audioCtx.currentTime` 是权威的「现在」，所有拍点都表达在它的时间轴上；setInterval 退化成一个 25ms 醒一次的「轮询泵」，唯一职责是在前瞻窗空了之前补货。它的精度要求被降到极低——25ms 的间隔误差完全被 120ms 的前瞻窗吸收，只要任何一次轮询的延迟不超过 120ms，队列就不断供。数值的取舍逻辑：轮询间隔取窗长的 1/4~1/5，既留足冗余又不空转。

「预排」还有个常被忽略的福利：可视化与声音天然对齐。摆锤动画同样由 audioCtx.currentTime 驱动（requestAnimationFrame 每帧读一次当前时间，算出离下一拍多远），而不是由 setTimeout 驱动——两座时钟不混用，动画和声音才不会各走各的。

## 拍长、重音与 Tap Tempo

拍长推导是纯算术：BPM（每分钟拍数）的倒数乘 60 即每拍秒数，120 BPM = 500ms，60 BPM = 1s。拍号决定重音周期：4/4 下每小节第一拍换重音音色（高频侧棒 vs 常规木鱼），强拍循环 = 拍号分子；6/8 的实际律动是两大拍各领三个小拍，重音周期与单纯按分子数又有讲究——工具里 2/4、3/4、4/4、6/8 各按乐理口径处理。

Tap Tempo（连点测速）是另一处「时钟题」：用户跟着心里的节奏连点按钮，工具取最近 8 次点击间隔的均值换算 BPM。两个细节决定手感：一是**丢尾**——用户停止点击后多久判定「这轮测速结束了」（太短误判、太长迟钝）；二是**防抖**——两次点击间隔短于人类极限（约 150ms）或长得离谱（如超过 2 秒）的样本要剔除，否则一次误触就把均值拉飞。均值而非中位数也是选择：连点节奏稳时两者无差，故意渐快渐慢时均值更贴近「当前的」速度。

## 同一家族的其他时钟题

精确调度只是节拍器的一半，另一半是「拍点检测」——从已录音频里反推 BPM 走的是自相关路线，与正向调度互为镜像（[BPM 检测的数学](/blog/articles/bpm-detection-autocorrelation/)里拆过）。而练琴场景的另一端，{{< tool id="guitar-tuner" >}}在线调音器{{< /tool >}}用 NSDF 自相关找基频——同一族算法在「找周期」这件事上通吃节拍与音高。节拍器、调音器、和弦图、音程听辨这些练习工具，连同录音降噪（[谱减法拆解](/blog/articles/fft-spectral-subtraction/)）、混音导出，都收在[音频创作工具箱](/collections/audio-creator-kit/)专题里，全部本地运行，节拍精度由硬件时钟背书。
